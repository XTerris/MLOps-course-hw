# Разбор пяти дефектов LoRA-обучения

Работа выполнена на собственном датасете GitHub Issues v2 из ДЗ 3–4:
2114 train и 268 validation-примеров. Оба варианта прошли полную эпоху,
по 265 обновлений. Причины дефектов установлены по исходному коду
коммита `222c09d`; сломанный полный прогон с lr=1e-2 не запускался.
Числа ниже получены исправленной реализацией. Исходный `tests/check.sh`
не изменён: отпечаток **06a02208c1f0**.

## 1. Валидация отсутствовала

В исходном `src/train.py` функция `evaluate` существовала, но не вызывалась:
`base_val=None`, а `curve_val` оставалась пустой. По train loss нельзя было
понять, улучшился ли адаптер относительно базы и не начал ли он запоминать
обучающие записи. Сохранение файлов модели этого не проверяет.

Теперь validation считается до первого обновления, каждые десять шагов и
в конце. Loss усредняется по числу токенов ответа после causal shift,
промпт и padding исключены. Примеры группируются по длине для экономии
padding; каждый замер использует все 268 записей. После оценки
восстанавливается режим модели, время оценки учитывается отдельно.

В каждом полном прогоне **28 точек**: 0, 10, …, 260, 265. У all_layers
val снизился с **0.636233 до 0.226786**,
у freeze14 — с **0.636233 до 0.238834**.
Кривые обоих вариантов находятся в [curves.png](curves.png).

## 2. Learning rate был завышен

В `params.yaml` стоял lr=1e-2. По лекции такой шаг вызывает скачки train
loss до десятков и ухудшение val даже без NaN. Ошибку нельзя диагностировать
только по факту завершения обучения или размеру сохранённого адаптера.

Learning rate снижен в 50 раз, до **2e-4**. Сохранены cosine schedule,
warmup 3%, ограничение нормы градиентов до 1 и эффективный батч 8.
При NaN/Inf цикл выдаёт ошибку вместо успешных метрик. Неполный хвост
накопления также даёт обновление оптимизатора.

Средний train loss первых 53 шагов all_layers — **0.3799**,
последних 53 — **0.2203**. Финальный val **0.226786**
сравнивается с базовым **0.636233**. Это числа validation
собственного датасета, а не перенос медицинского эталона из лекции.

## 3. Заморозка первых 14 слоёв не работала

Функция `lora_config` получала `n_layers` и `freeze_first`, но не использовала
их. Поэтому оба варианта навешивали LoRA на все 28 слоёв; название freeze14
не соответствовало эксперименту, а сравнение времени и качества было ложным.

Теперь `layers_to_transform` задаёт диапазон от `freeze_first` до последнего
слоя. В all_layers это **0–27**, в freeze14 — **14–27**. База заморожена в
обоих случаях: заморозка нижних слоёв здесь означает отсутствие их адаптеров.
Embedding и lm_head не обучаются и не сохраняются целиком.

Обучаемых параметров **5,046,272 против 2,523,136**,
ровно вдвое меньше. Время обучения — **1849.4 / 1692.8 с**;
наблюдаемый пик MPS — **6427.7 / 5427.7 МиБ**.
Val в конце — **0.226786 / 0.238834**.
Это по одному запуску на вариант, поэтому разница времени зависит от
фоновой нагрузки и не является статистически устойчивым бенчмарком.

## 4. Адаптер нельзя было передать вместе с токенизатором

Исходное обучение вызывало только `model.save_pretrained`. Compare загружал
токенизатор по имени базы из локального конфига, поэтому отсутствие файлов
в папке адаптера оставалось незаметным на авторской машине. У получателя
не было токенизатора, chat template и настроек инференса.

Теперь рядом с матрицами сохраняются `tokenizer.json`, `tokenizer_config.json`,
шаблон чата и `inference_config.json`. В конфигурации адаптера зафиксирована
ревизия базы. Compare читает токенизатор из переданной папки с
`local_files_only=True`; `enable_thinking=false` совпадает с ДЗ 4.
Базовые веса нужно иметь в HF-кеше отдельно — LoRA их не содержит.

Матрицы all_layers занимают **19.3 МиБ**, вся папка —
**30.21 МиБ**. У freeze14 — **9.65 / 20.56 МиБ**.
`modules_to_save` отсутствуют: словарь не попадает в адаптер. Проверка 4
копирует папку в новый каталог, запрещает сеть и сопоставляет все пять
ответов с результатами [compare.md](compare.md).

## 5. Seed не применялся к инициализации и dropout

В `src/runtime.py` была `set_seed`, но обучение её не вызывало. Shuffle
получал собственный seed, однако LoRA и dropout оставались случайными:
два запуска с одинаковым конфигом были разными экспериментами.

Теперь Python, NumPy и PyTorch получают **seed 42 до создания модели и LoRA**;
включены детерминированные операции. Генерация использует
`do_sample=False`. Для сокращения логитов выбран непрерывный срез, поскольку
индексная выборка требовала недетерминированного `index_put` backward на MPS.
Детерминизм ради обхода ошибки не отключается.

Исходная проверка запускает два независимых обучения по три шага и сравнивает
loss после округления до четырёх знаков. Фактическая кривая: **[0.5211, 0.7505, 0.3954]**.
Короткие прогоны хранятся во временной папке и не заменяют полные адаптеры.
Подтверждается воспроизводимость на текущих версиях ПО и MPS; идентичность
между разными устройствами не проверялась.

## Дополнительная корректность и приёмка

Все 2114 train-примеров обработаны: **265 обновлений, 772903 входных токена**
за эпоху. Градиенты нормируются по числу токенов ответа эффективного батча,
включая последнюю неполную группу. Скорость считается по фактическим токенам.
Время MPS измеряется с синхронизацией. Память — выборочный максимум
`torch.mps.driver_allocated_memory`, включая кеш, а не непрерывный аппаратный пик.

Шесть дополнительных тестов проверяют совпадение полного и сокращённого
loss/градиентов, взвешенную валидацию, неполный хвост двух эпох,
эквивалентность накопления физическому батчу, заморозку и отказ при пустой
маске ответа. Все шесть прошли. Артефакты обучения и тензоры исключены из
Git, но кешируются DVC. Все девять исходных проверок прошли. Пять ответов при офлайн-загрузке совпали дословно. Два независимых запуска по три шага дали одинаковую train-кривую **[0.5211, 0.7505, 0.3954]**.
