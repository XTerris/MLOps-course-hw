# ДЗ 8–10. Выпуск модели и локальный API

Шуликов М. В. · 30 октября 2026 года

## ДЗ 8–10: выпуск модели и API

Задание объединяет расследование семи дефектов процесса выпуска, оркестрацию через Prefect, проверку качества и локальный API модели. Исходный учебный проект сохранён отдельно. Таблица [defects.csv](../defects.csv) связывает семь причин с воспроизведением и регрессионными тестами.

Кандидат из ДЗ 6–7 ранее получил отказ из-за регрессии критического среза `bug`. Назначенного `champion` нет. Поэтому настоящее обслуживание базовой модели в этой работе показано в **диагностическом режиме**: это проверка загрузки и ответа, а не свидетельство успешного допуска или существования ранее принятого выпуска. Синтетические версии A и B используются только для проверки управления процессом.

## Семь дефектов

Найдены ошибки ключа кеша, проверки отчёта, атомарной записи, повторной публикации, готовности сервиса, определения загруженной версии и проверки запроса. Для каждой из семи причин собственный регрессионный тест выявляет ошибку исходного прототипа и проходит на исправленном коде. Сохранены [журнал исходного прогона](../evidence/before-integration.log) и [журнал исправленного прогона](../evidence/after-integration.log).

## Процесс выпуска

Поток состоит из четырёх задач: `prepare-input`, `obtain-and-verify-artifact`, `evaluate-release` и `publish-release`. Подготовка проверяет строки JSONL и обязательные поля примеров; длина input ограничена 8192 символами. Все 52 записи golden проходят проверку, максимальная длина — 1670 символов. Ключ кеша включает SHA-256 содержимого, ревизию токенизатора, хеш шаблона, максимальную длину и версию кода обработки. Результат задачи хранится на диске; массив весов через Prefect не передаётся.

[Отчёт допуска кандидата](../results/candidate-release-report.json) получен вызовом прежнего `quality_gate` после сверки отчётов, сырых ответов и их хешей. Файлы адаптера восстановлены из реального training run в локальном MLflow и захешированы; веса не включены в репозиторий. Старые отчёты сами не содержали `model_sha256` и `runtime_sha256`, поэтому одного расчёта этих хешей сейчас недостаточно для доказательства положительного решения. Результат остаётся отказом.

## Сбой и восстановление

В опыте взята копия настоящего golden set из 52 строк, а выпуски A и B представляют собой помеченные `STUB ONLY` фикстуры. Искусственный сбой после подготовки завершил процесс с кодом 1. Следующий процесс показал состояние задачи `Cached` и завершился с кодом 0. После изменения байтов входного файла по тому же пути задача снова выполнилась. Ещё один сбой внесён после замены указателя и до записи события: повтор восстановил событие, а следующий повтор не создал дубль. Последовательность смен A и B зафиксирована в журнале. При отказе реального кандидата SHA-256 учебного указателя до и после одинаков: `0bb6ec1a07f2c71016d90b62af8865121cb2b7b4bc8d6cd5d0336af99ad0a7d3`; указатель не представляет принятую реальную baseline.

Сводка кодов возврата и событий — [prefect-summary.json](../evidence/prefect-summary.json); отдельные журналы `prefect-01`…`prefect-07` содержат команды, имена запусков и состояния задач. Сбой и восстановление демонстрируют поведение файлового хранилища при одном писателе; конкурентная публикация несколькими писателями не проверялась.

## Проверка качества кандидата

Базовая модель — `Qwen/Qwen3-0.6B`, ревизия `c1899de289a04d12100db370d81485cdf75e47ca`. Кандидат — `models:/my-qwen-adapter/1`, training run `93842900641d4cca87da85158f95b855`. В оценке использованы 52 вопроса, четыре среза и три behavioral-кейса; критическими заранее выбраны `bug` и `documentation`.

Обе модели получили accuracy 38/52 и format rate 47/52. На срезе `bug` baseline ответил правильно на 8 из 13 вопросов, кандидат — на 7 из 13. Gate отклонил кандидата. Базовая модель также не прошла один behavioral-кейс, поэтому сравнение baseline с самой собой не превращает её в прошедший gate выпуск. Повторное обучение и sweep не выполнялись.

Протокол задаёт ту же system-инструкцию, детерминированную генерацию, `enable_thinking=false`, seed 42 и максимум 32 новых токена. Отчёты и сырые ответы ДЗ 6–7 сохранены в `../HW 6-7/metrics`; golden и behavioral-наборы находятся в `../HW 6-7/data/eval`. Последний каталог управляется DVC, поэтому преподавателю нужен доступ к его данным: локальный DVC remote сам по себе недоступен из удалённого клона.

## Контрактные и интеграционные проверки

Всего добавлено девять интеграционных тестов: три обращаются к локальному HTTP-серверу, остальные проверяют процессы и файловую систему, включая повреждение файла и восстановление после сбоя между указателем и журналом. Последние два дополнительных случая проверяют исправленную систему; их не следует считать отдельным доказательством red→green исходного прототипа. Приложенные 13 контрактных тестов и 24 теста ДЗ 6–7 также запускаются без загрузки модели.


Локальный `make check` запускает контрактные и интеграционные тесты без весов. Отрицательный прогон семи тестов на исходнике завершается ненулевым кодом; после исправлений те же проверки проходят. Удалённый GitHub Actions не запускался, защиту merge эта работа не подтверждает.

| Изменение | Действие |
|---|---|
| Код процесса или API | `make check`; при изменении генерации — повторить полную оценку. |
| Данные или параметры подготовки | Проверить схему и новый ключ кеша; при изменении данных оценки — повторить оценку. Необходимость обучения зависит от роли изменённых данных. |
| Новый адаптер | Проверить файлы и загрузку, выполнить полную оценку и gate до публикации. |

Команды подготовки окружения, восстановления артефакта, запуска flow и API приведены в [README.md](../README.md).

## Локальный API

`GET /health` подтверждает работу процесса; `GET /ready` сообщает о готовности только после проверки файлов, загрузки и прогрева. `POST /generate` отклоняет некорректный prompt или лимит до вычисления. Ответ содержит текст, ID запроса, фактически загруженный `model_id`, SHA-256 runtime, количество выходных токенов и длительности.

При отдельном запуске настоящей базовой модели на MPS API вернул `{"answer": "bug"}`, семь выходных токенов и `diagnostic_only=true`. Полный запрос и ответ — в [real-smoke.json](../results/real-smoke.json). Файлы модели и токенизатора проверены по SHA-256, а manifest восстанавливается из локального снимка закреплённой ревизии. Его абсолютный путь нужно пересоздать на другой машине.

## Переключение и откат

Тестовый опыт использует версии `fixture-A` и `fixture-B`. После публикации B работающий процесс продолжает отвечать как A; после перезапуска загружается B. Откат к A и новый перезапуск возвращают ответы A. Это подтверждает поведение указателя и памяти процесса, но не является оценкой качества реальной модели.

## Небольшой замер

После прогрева выполнены одинаковые запросы с лимитом 32 токена. В каждом режиме — восемь запросов; все 16 завершились успешно, каждый ответ содержал семь выходных токенов.

| Параллельность | Успехи / ошибки | Пакет, с | Запросов/с | Средняя задержка, с | Максимум, с |
|---:|---:|---:|---:|---:|---:|
| 1 | 8 / 0 | 1,450 | 5,516 | 0,181 | 0,189 |
| 2 | 8 / 0 | 1,575 | 5,078 | 0,365 | 0,443 |

Все отдельные попытки сохранены в [benchmark.json](../results/benchmark.json), включая клиентскую задержку, длительность генерации, ID модели и запроса. Генерация в backend выполняется последовательно под блокировкой: при двух клиентах второй запрос ждёт завершения первого. `waiting_seconds` включает подготовку токенов и ожидание блокировки, поэтому это не чистое время очереди.

Выборка слишком мала для устойчивой оценки p95. Измерена полная задержка JSON-ответа, а не TTFT или ITL. Prefill обрабатывает входные токены; decode последовательно генерирует выходные. KV-cache хранит промежуточные состояния и расходует память в зависимости от длины и числа активных последовательностей. Этот локальный последовательный Transformers-сервис не измеряет производительность SGLang или vLLM.

## Ограничения и дальнейший выпуск

Для отката нужен ранее принятый manifest и согласованный с ним отчёт, после изменения указателя сервис необходимо перезапустить и проверить фактически загруженный ID. Синтетический откат проверен; утверждать наличие допущенной реальной baseline-версии по данным ДЗ 6–7 нельзя. Если изменятся модель, данные оценки или условия генерации, требуется новая полная оценка; фиктивный `passed=true` не заменяет её.

Запись видео в этот этап не входит. HTML-презентация отчёта подготовлена отдельно.
