# ДЗ 1. Окружение, первый инференс и бенчмарк

## 1. Окружение и структура проекта

Сначала создал Git-репозиторий в `hw1-broken` и сохранил исходные файлы
без исправлений в initial commit. Служебный `.DS_Store` в него не включал.
Затем настроил окружение и только после этого перешёл к Python-коду.

`uv` и Python 3.12 уже были установлены. Повторять установщик uv и создавать
вложенный проект через `uv init` не понадобилось: в заготовке уже был
`pyproject.toml`. Выполнил `uv add --python 3.12` для зависимостей задания,
добавил недостающий `psutil`, указал точные версии прямых зависимостей
и выполнил `uv sync`. Проверка импорта показала PyTorch 2.14.0 и доступный MPS.

Таким образом, шаги с uv выполнил до исправления генерации и бенчмарка.
После подготовки окружения исправил дефекты, мешавшие корректным запускам;
их разбор вынес в раздел 5, как в задании. Дальше сначала выполнил инференс
и замер базовой 0.6B, затем выбрал модель по профилю машины и повторил замер.

Версия Python закреплена в `.python-version`, а `requires-python` ограничен
веткой 3.12. Все транзитивные зависимости записаны в закоммиченный `uv.lock`.
Команды Makefile используют `--locked`, чтобы изменение зависимостей
не приводило к незаметному обновлению окружения во время запуска.
Полный снимок версий сохранён в [environment.json](results/environment.json).

Каталоги `src/`, `tests/`, `docs/`, `data/` и `conf/` на месте. Последние два
пока пустые и сохранены через `.gitkeep`: для этого задания внешний датасет
не нужен, а дублировать `params.yaml` в `conf/` было бы лишним.

## 2. Конфигурация и первый инференс 0.6B

Для первого запуска оставил базовую Qwen3 размера 0.6B из задания.
Её имя загрузчик получал через `load_params()` из `params.yaml`, а не
из константы в Python. Там же задал `dtype: bfloat16`, `device: mps`,
`max_new_tokens: 200`, `temperature: 0.0`, `seed: 42`
и `enable_thinking: false`.

Код загрузки и генерации общий для `src/generate.py` и `src/bench.py`.
Промпт собирается через `apply_chat_template`, вход переносится на
устройство модели, а при выводе из результата отрезаются входные токены.
Seed фиксируется до загрузки модели, при нулевой температуре используется
жадный поиск. Thinking отключён через параметр шаблона, а не удалением
рассуждений из уже готового ответа.

Первый запуск `uv run --locked python -m src.generate` скачал базовую модель
и выполнил инференс. На промпт «Объясни, что такое MLOps, в трёх предложениях.»
модель ответила:

> MLOps — это совокупность практик и инструментов, направленных на интеграцию и управление машинным обучением в производственных и бизнес-процессах. Это включает в себя интеграцию данных, оптимизацию модели, контроль качества и автоматизацию процессов.

Выдано 76 новых токенов. Полный сохранённый вывод повторного запуска базовой
модели лежит в [baseline-generation.txt](results/baseline-generation.txt).
В нём нет входного промпта и блока рассуждений.

В условии говорится о первых 200 токенах, а в примере кода используется
`max_new_tokens: 200`. Поэтому это ограничение сверху: модель может
закончить раньше по EOS. Принудительно продлевать ответ до 200 токенов
не стал. При этом просьбу дать три предложения базовая модель не выполнила:
получилось два. Это ограничение качества ответа, а не ошибка подсчёта токенов.

## 3. Бенчмарк базовой модели

После первого инференса запустил `HF_HUB_OFFLINE=1 make bench` для 0.6B.
Загрузка из локального кэша заняла **0,5320 с**, медианная скорость составила
**74,19 токена/с**, пиковая RSS — **2009,5 МиБ**. Три метрики записаны отдельно
в [baseline-bench.json](results/baseline-bench.json).

### Методика измерения

Для обеих моделей использовал один промпт:

> Объясни, что такое MLOps, в трёх предложениях.

Настройки: не более 200 новых токенов, `temperature: 0.0`, `seed: 42`,
`enable_thinking: false`. Перед тремя измеряемыми прогонами делал один
прогрев. Каждый бенчмарк запускался отдельным процессом; параллельных
запусков моделей во время измерений не было. Другую нагрузку всей системы
специально не контролировал, поэтому это замер рабочего ноутбука,
а не изолированного стенда.

Веса предварительно скачал обычным запуском генерации. Сам бенчмарк
запускал с `HF_HUB_OFFLINE=1`, то есть время скачивания и обращения к Hub
не смешивались со временем локальной загрузки. Файлы уже находились
в кэше; кэш файловой системы перед замером не очищал.

Три метрики разделены следующим образом:

- **Загрузка:** время работы `load_model`, включая seed, токенизатор,
  веса, размещение модели и ожидание готовности MPS. Импорты Python
  и запуск интерпретатора в этот интервал не входят.
- **Скорость:** фактическое число новых токенов, делённое на время одного
  вызова генерации. Промпт подготовлен заранее, декодирование текста
  не измеряется. Prefill внутри `model.generate` входит в замер;
  это не отдельный тест чистого decode. Устройство синхронизируется
  перед началом замера и до остановки таймера, чтобы учесть завершение
  GPU-операций.
  Итог — медиана трёх скоростей, а не среднее.
- **Пиковая RSS:** `resource.getrusage(...).ru_maxrss` за весь процесс,
  включая загрузку и прогрев. На macOS байты переведены в МиБ делением
  на 1024²; на Linux исходная величина в КиБ делится на 1024.
  Название поля `peak_rss_mb` оставлено из заготовки, но единица — МиБ.

RSS — это память процесса, а не отдельный счётчик VRAM и не вся занятая
память компьютера. На Apple Silicon память общая, поэтому складывать
эту цифру с какой-либо «памятью видеокарты» некорректно. CPU-прогоны
в float32 и bf16 не проводил; превосходство bf16 на CPU не утверждаю.

## 5. Найденные дефекты

### 1. Имя модели было захардкожено в трёх местах

В `src/model.py` загрузчик игнорировал значение из YAML. Кроме того,
`src/generate.py` печатал фиксированное имя, а `src/bench.py` записывал
его в JSON. При замене модели в конфиге продолжала загружаться старая;
подпись и отчёт тоже могли вводить в заблуждение.

Убрал все три строки-константы. Загрузчик, подпись и результат бенчмарка
теперь читают `params["model"]["name"]`. Общая загрузка осталась в одном
модуле, отдельной реализации для бенчмарка нет. Unit-тест передаёт
постороннее имя и проверяет аргументы обоих `from_pretrained`.
Полная самопроверка дополнительно подменяет модель на маленькую
альтернативу и проверяет `model.config.name_or_path` после загрузки.

### 2. Зависимости не были зафиксированы

В `pyproject.toml` были просто названия пакетов без версий, а `uv.lock`
отсутствовал. В этой заготовке отдельного `requirements.txt` нет,
хотя в описании задания симптом приведён на его примере. Суть та же:
две установки в разное время могли получить разные версии библиотек.

Указал точные версии прямых зависимостей, добавил `psutil`, создал
и закоммитил lock-файл. `uv lock --check` проверяет его соответствие
`pyproject.toml`. Сам по себе lock-файл фиксирует библиотеки, но не
неизменность весов на Hub: ревизии реально загруженных моделей отдельно
сохраняются в JSON бенчмарков.

### 3. Бенчмарк смешивал загрузку и генерацию

Единственный таймер запускался перед загрузкой модели и больше
не сбрасывался. Поэтому в знаменатель первой скорости попадала загрузка,
а следующих — ещё и предыдущие генерации. При этом `load_time`
оставался равным нулю, а указанного в конфиге прогрева фактически не было.

Разделил загрузку, прогрев и измеряемые запуски. Для каждого из трёх
прогонов запускается новый таймер, а скорость вычисляется по реальному
числу выданных токенов, не по лимиту 200. Токенизацию и декодирование
вынес из измеряемого участка. Добавил ожидание MPS/CUDA: без него
асинхронный ускоритель можно было бы измерить до завершения работы.

Медиана и функция пиковой RSS уже были в заготовке — их не пришлось
изобретать заново. Сохранил их и добавил проверки. В тесте с искусственными
таймерами загрузка занимает 5 секунд, а генерации — 2, 4 и 1 секунду.
Проверяется, что скорости равны 50, 20 и 90 токенам/с, итоговая медиана — 50,
и прогрев в этот список не попал.

### 4. Генерация не была воспроизводимой

В YAML стояла температура 0.7. Функция `set_seed` уже существовала,
но ни одна точка входа её не вызывала: наличие `seed: 42` в файле само
по себе ничего не меняло. При сэмплинге это допускало разные ответы
между запусками.

Поставил температуру 0 и вызов фиксации seed в общий загрузчик до создания
модели. Так одинаковая настройка применяется и к генерации, и к бенчмарку.
Фиксируются `random`, NumPy и PyTorch. Для нулевой температуры используется
`do_sample=False`, а параметры сэмплинга нейтрализованы; для положительной
температуры остаётся поддержка сэмплинга. Seed не является обещанием
побитового совпадения на любом другом устройстве или версии библиотек.

### Дополнительные проблемы в самопроверке и токенизации

Исходный `check.sh` не проверял успешность двух запусков генерации.
Если оба падали и оставляли одинаковый stdout, `diff` мог показать успех.
Теперь отдельно проверяются коды завершения и непустой вывод, а ошибки
не скрываются. Для временных файлов используется отдельный каталог,
исходный конфиг восстанавливается через `trap`, в том числе при ошибке
или обычном прерывании. Подмена имени больше не зависит от варианта
`sed -i` на macOS и Linux.

Ещё одна слабость проверки: поиск слов `warmup` и `load_time` проходил
даже на исходном коде с TODO-комментарием и нулевым временем загрузки.
Заменил его настоящими unit-тестами таймеров. Отдельные тесты самого
shell-скрипта проверяют, что упавшая генерация не выдаётся за успех
и что конфиг после проверки восстановлен.

Chat template, `enable_thinking`, обрезка входного промпта, `eval()`
и `inference_mode()` уже были реализованы в заготовке. Их сохранил.
При токенизации готового chat template добавил `add_special_tokens=False`,
чтобы токенизатор не добавлял служебные токены второй раз у моделей,
где это привело бы к дублированию.

## 6. Проверки и повторный запуск

Полный `make check` прошёл и с доступом к сети, и повторно с
`HF_HUB_OFFLINE=1`, когда обе нужные ему модели уже были в кэше.
Логи сохранены в [check-online.log](results/check-online.log)
и [check.log](results/check.log). Проверка действительно загрузила
альтернативную модель, а затем вернула исходный `params.yaml`.
Все 14 unit-тестов также прошли.

Два запуска генерации, выполненные отдельными процессами, дали побайтово
одинаковый stdout. Помимо проверки через `diff` в `check.sh`, отдельно
сравнил сохранённые [первый](results/generation.txt)
и [повторный](results/generation-repeat.txt) выводы через `cmp`.
Их общий SHA-256:

```text
1820d2804eb82b36b857684115698906bff4677a306f529070426d189c5109fe
```

Команды ниже повторяют **итоговый** запуск на 1.7B из текущего `params.yaml`:

```bash
uv sync --locked
make generate
HF_HUB_OFFLINE=1 make bench
make check
```

На первом `make generate` нужен интернет для скачивания выбранной модели.
Первый `make check` дополнительно скачивает альтернативную. После этого
и его можно запускать с `HF_HUB_OFFLINE=1`. Новый бенчмарк перезапишет
`docs/bench.json`, но не сохранённые для этого отчёта файлы в `docs/results/`.
Результаты скорости и памяти при повторении могут немного измениться.

Чтобы повторить всю последовательность ДЗ, а не только итоговый запуск,
сначала нужно указать в `model.name` базовую модель из поля `model` файла
`docs/results/baseline-bench.json` и выполнить генерацию и бенчмарк.
После этого заменить имя на выбранное по профилю из `docs/results/bench.json`,
повторить генерацию и бенчмарк и выполнить `make check`.
В обоих случаях меняется только `params.yaml`; JSON-файлы здесь служат
записью прошлых запусков, а не конфигурацией для Python-кода.
